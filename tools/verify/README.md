# UI回帰チェック

```bash
npm run verify
```

`dist/easysmarky.iife.js`(実際の配布物)を、Smarky の API をスタブしたページに読み込ませ、
ヘッドレス Chromium で操作して挙動を検証する。**Smarky への接続もログインも不要。**

- `harness.html` — `window.fetch` を差し替えて Smarky の API を模した検証ページ。
  ページ画像は canvas で生成する。`window.__esAssert()` / `window.__esView(mode)` を公開している
  (mode は `list` / `view` / `edit`)
- `drive.mjs` — 静的サーバの起動 → Chromium 起動 → CDP 操作 → 判定 まで行う。
  playwright/puppeteer は使わず、Node のグローバル `WebSocket` で CDP を直接叩いている
  (Node 22未満だと `WebSocket is not defined` で落ちる。`package.json` の `engines.node` 参照)
- 出力(スクリーンショット)は `out/`(gitignore 済み)

`chromium` 以外を使う場合は `CHROME_BIN=google-chrome-stable npm run verify`。

## 注意点

### `base_sheet` に `width` / `height` を足さないこと

**実機の `base_sheet` に `width` / `height` は存在しない。** rim の座標系は
`correct_image_size`(ページごとの `[w,h]` を並べたフラット配列)から取る。

v0.6.0 以前のハーネスは `base_sheet: { width: 1000, height: 1400 }` という実機には無い形を
返していた。そのため `report.base_sheet.width` を座標系の出所にしていたコードが全部通って
しまい、**実機では解答用紙の枠が1つも出ていない**(座標系が取れず `pageViewer` が枠の描画を
丸ごと諦める)ことを検出できなかった。主要導線「解答欄をタップして入力に入る」が死ぬ
バグを、ハーネスの形が実機と違うというだけで見逃していた。ここは実機に合わせ続けること。

### ダミーのページ画像は必ず座標系と違う解像度にすること

`rim` と `cut_margin` は `correct_image_size` の座標系であって、ページ画像のピクセルとは
別物として扱う(実機では一致していたが、一致を前提にはしない)。`src/ui/cropPreview.ts` は
`naturalWidth`/`naturalHeight` との比で換算する。

ハーネスの画像を座標系と同じ解像度で作ると、この換算を落としても、逆に `naturalWidth` を
rim の座標系だと思い込んでも全部通ってしまう。そのため解答用紙は 2.0 倍・1.25 倍、
問題ページは 1.5 倍と、座標系とも互いとも違う倍率にしてある。**ページごとに用紙サイズも
解像度も変えてある**(`correct_image_size` がページ単位で持つ以上ありうるので、全ページ
共通の1組だと思い込む実装をここで落とす)。

`RIMS` の塗り色は、切り出した範囲が本当に解答欄と重なっているかを `getImageData` で
1画素見て確かめるための目印。設問3(2ページ目・`rim: [0, 800, 760, 120]`)は用紙の左端に
接しており、切り出しのクランプも見ている。

### 縦長の解答欄(設問オ)を消さないこと

`RIMS` の設問オ(2ページ目・`rim: [620, 300, 100, 260]`)だけが**縦長**で、他は全部横長。
横長の解答欄は表示サイズが幅で先に頭打ちになるため、**canvas の `max-height` が効く経路を
一度も通らない**。設問オはその経路を必ず通すためだけに置いてある(スマホ幅・PC幅の
どちらでも上限に当たる縦横比 0.518 にしてある)。

これが無かった v0.8.0 では、`fieldEditor.ts` が canvas の**幅だけ**を px 指定して高さを
`height:auto` に任せていたため、`max-height` が高さだけを切り詰めて**プレビューが横に
5倍ほど引き伸ばされていた**(実機で丸囲みの ⓐⓑⓒ が楕円になり、縦罫線が太い黒帯になって
いた)。それでもハーネスは 84 件すべて通っていた。CSS が縦横比を保つのは `width` と
`height` が**両方 `auto`** のときだけなので、片方でも明示するなら両方 JS で決めること。

設問オは**最初から入力済み**にしてある。空にすると「次の未入力へ」がここで止まり、
末尾から先頭へ巻き戻る検査(`nextEmptyWrap`)が成立しなくなる。また**2ページ目に置く**こと。
設問は `page → id` 順に並ぶので、1ページ目に置くと設問ストリップの添字がずれて
`skipLocked` / `autoZoom` / `autoPan` / `stripNav` の検査を巻き込む。

### 解答欄プレビューの表示サイズは canvas ではなくスロットが決める

`.es-preview-slot` の幅を `ResizeObserver` で見て、`updatePreview()` が canvas の CSS の
**幅と高さの両方**をそこから決める。**canvas 自身を観測してはいけない**(測る→広げる→
また発火 の無限ループになる)。同じ理由で、スロットは中身に押し広げられないよう
`min-width: 0` と `flex-basis` の % で幅を決めている。

高さの上限の出所は `styles.ts` の `.es-preview-wrap canvas.es-crop { max-height: … }` ひとつ
だけで、`updatePreview()` が `getComputedStyle().maxHeight` で読む(ブレークポイントを
TS 側に複製しないため)。したがって `max-height` は px / vh / min() など**絶対長に解決される
値**で書くこと。% にすると読めず「上限なし」になる。

**幅だけ決めて `height:auto` に任せてはいけない**(上の「縦長の解答欄」参照)。
高さを明示しても `ResizeObserver` は 1 tick 余分に回るだけで収束する
(2回目は同じ値になり、`updatePreview()` が style への再代入自体をスキップする)。

### プレビューの初回描画は ResizeObserver に依存している

v0.7.x までは、スマホの入力ペイン `.es-pane-form` が `data-mode="view"` の間
`display: none` で始まり、解答欄をタップして編集モードに入ったときの
`ResizeObserver` 発火だけがプレビューの初回描画経路だった。現在は問題ビューア
(`.es-pane-question`)と入力ペイン(`.es-pane-form`)を常時両方表示する上下分割
レイアウトになったため、初回描画は他の要素(PC)と同じく `drawCropPreview().then()` 直後の
`requestAnimationFrame(updatePreview)` 経路で素直に走る。
ただし `ResizeObserver`(`.es-preview-slot` を監視、`src/ui/fieldEditor.ts`)自体は、
幅変更(画面回転・ウィンドウリサイズ)に追従してプレビューを再描画するために引き続き必要。
`updatePreview()` のキャッシュ(`lastRendered`)を早期return の分岐で更新してしまうと、
非表示中(幅0)の呼び出しが「前回と同じ」と誤判定され、以後永久に描かれなくなる点は変わらず
落とし穴として残っている。

### `--virtual-time-budget` は使わないこと

仮想時間ではレンダリング更新が実時間どおりに走らず `ResizeObserver` が配信されないため、
「幅変更後にプレビューが再描画されない」という**偽の不具合**が出る。
同じ理由で、ブラウザウィンドウが不可視(`document.hidden === true`)だと
`requestAnimationFrame` が止まり `ResizeObserver` も発火しない。

### Shadow DOM の外に出るイベント

キーボードショートカットは `window` の capture で受けている(オーバーレイのどこに
フォーカスがあっても効かせるため)。ハーネスから合成イベントで叩くときは
`composed: true` を付けないと Shadow DOM の境界を越えない。

### 押せるかは実マウス操作と hit-test で見る

JS の `element.click()` は、要素が別の要素に隠れていても成功する。設定ダイアログが
全画面の `.es-root` の下に隠れて押せなかった不具合(v0.14.0)は、JS のクリックの検査では
すり抜けた。ボタンやチェックの押下を確かめるときは、`Input.dispatchMouseEvent` で押し、
`shadowRoot.elementFromPoint()` が目的の要素を返すことも見る(`assertSettingsClickable`)。

実マウス操作は、ページにユーザー操作を与えるので、未保存の入力があるページでは
離脱の確認(`beforeunload`)が次の `Page.navigate` を止める。実マウス操作の検査は
一覧の新しいページで行い、未保存の入力のある画面の後ろで走らせないこと。

### スタブの保存はステートフル

`/api/student/digital_report/save` を受けると、送られた `param_base_sheet_fields` の
`answer_texts` をスタブ側の状態に書き戻す。これにより `src/save/save.ts` の
「保存 → 再取得 → 送ったテキストが反映されているか照合」が本物どおり動く。
ステートレスにすると照合が必ず失敗するので、この挙動は維持すること。

### 一覧の進捗は localStorage 由来

一覧の「3/8」と「手書きあり・保存不可」は、一度開いた回の要約を
`easysmarky:summary:{studentCode}` に残したものを読んでいる。ハーネスは実行のたびに
`easysmarky:` で始まるキーを消してから始めるので、一覧の進捗欄は「—」で始まる。

### `goTo` はズームを保持する。設問エ(id:4)は編集不可

`pageViewer.ts` の `goTo()` はページ切替のたびにズーム・スクロールをリセットしていたが、
設問文が解答用紙画像上にしかない実機の構成では「切り替えるたびに探し直す」原因になって
いたため、ズームは保持するよう変更した(スクロールのリセットも `showField()` 経由の
ジャンプでは行わない)。`RIMS` の設問エ(`answer_type: 5` の画像型)は編集不可設問の
経路(自動パン・Shift+↵ のスキップ)を検証するための専用フィールドで、`fields` は
`page→id` 順に並ぶため設問順は ア・イ・エ・ウ・オ・カ・キ になる。
選択式は選択肢があれば編集できるので、設問エの役目は画像型が担う。
`answer_type` は公式 app.js の AnswerTypeEnum と同じ値(1 手書き・テキスト / 2 手書きのみ /
3 テキストのみ / 4 選択肢 / 5 画像)。設問ウ(3)は編集でき、設問キ(2・末尾)は編集不可で
「手書きのみ」の理由を出す。

### 記号問題(カ・選択式)は既存の答えを持たせて末尾に置く

`RIMS` の設問カ(`answer_type: 4`・`choice_texts: ["ア","イ","ウ","エ"]`)は、既存の答えとして
「ウ」を `answer_texts[0]` に持つ。公式の生徒画面は選択肢を `choice_texts` から直接並べ、
答えを `answer_texts[0].text` に入れるので、その形を再現している。2ページ目の末尾に置いて
ア〜オの「次の未入力へ」の連鎖を変えないようにしてある(入力済み・件数の検査は ア・オ・カ が最初から入力済み)。

検査は「選ぶと枠に文字が出る」「←→で前後へ(無回答を挟んで巡回)」「無回答で消えて入力済みが1つ減る」
「保存では選んだ記号が中央に置かれて送られる」「無回答は 1x1 の空スタンプとして送られる」を見る。
保存の送信内容は `POST_LOG` の `answerTexts` に残している。

### 検証していないこと

実機の Smarky でしか確認できないものは対象外:
rim の枠が実際の解答用紙とどれだけ合うか、iOS Safari の `100dvh` とソフトキーボード表示時の
レイアウト、読むモードの実機での読みやすさ(国語の問題文は解答用紙画像に印字されていると実機で確認済み)、実サーバへの保存、
ユーザースクリプト版の「別タブで開く」。
ヘッドレスでは `visualViewport` の高さが変わらないので、キーボード追従は擬似オブジェクトで検証している
(実機の `offsetTop`・Android Chrome で innerHeight も縮むかどうかは未確認)。
誤クリック抑止(静止した2本指タップで枠が選ばれない)も、ヘッドレスでは click が出ないため検査で検出できない。
iOS Safari はページ全体のピンチ拡大が `touch-action` で止まらない場合がある。
窓の中のピンチと、一覧の慣性スクロール中に離れたときの位置は実機で確認する。
未保存時の確認ダイアログそのもの(ハーネスは `beforeunload` が `preventDefault` されるかと、
`window.confirm` に渡される文言だけを見る。ダイアログは CDP を止めるので実際には出さない)。

常時上下分割レイアウト(v0.8.0〜)は、ハーネスの検証高さ(430×900)より低い実機
(iPhone実機やDevToolsのモバイルエミュレーションで 430×700 程度)での見え方も対象外。
特にソフトウェアキーボード表示時にテキストエリアが隠れないか、rimタップ時の自動ズーム/
パンで直前の設問文が視界に残るか(`src/ui/pageViewer.ts` の `focusActiveRim()` が
ビューアの実高さに応じてズーム上限・パンオフセットを切り替える閾値 `vh < 320` は仮置き)は、
実機・DevToolsでの目視確認が必要。

スマホの解答欄プレビューの高さ上限 `min(200px, 26vh)`(v0.8.1〜)が、実機の縦長の解答欄で
「読める大きさ」と「textarea まで指が届く」を両立できているかも目視確認の対象。
`.es-editor-body` は元々スクロールする(textarea の `min-height: 150px` だけで
ペインの高さを超える)ので、上限を上げたぶんだけ textarea が下へ送られる。
